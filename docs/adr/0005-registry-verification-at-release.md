# Registry verification in one review before the v1 release

> Back in force (Micah, 2026-10-09). ADR 0008 replaced this decision with verification at each slice close, and was amended the same day: registry verification is in the v1 release review again, as decided below, and nothing blocks a slice's build. Two additions come from ADR 0008: a registry review workbook is produced at each slice close, so entries can be verified early when the engineer chooses, and his verdicts are applied to the registry by an agent ("Applying the verdicts", docs/brief/verification.md). The governing-case recompute stays at release (ADRs 0006, 0007).

> "The rest of ADR 0004 is unchanged" below no longer holds for the governing-case calc: from slice 2 on it is not blind and is deferred to this same release review (ADR 0006, 2026-10-04). The section cited below as "The release registry review" is now "The release review" in docs/brief/verification.md, which describes the current process.

Supersedes the per-slice registry verification in ADR 0004. ADR 0004 had the engineer of record verify each slice's drafted registry entries within that slice, before the independent calcs ran, so the independent calc could work from verified values. Instead he verifies every drafted entry in one review in the v1 release slice (docs/ROADMAP.md, slice 9), and no slice's "done when" includes registry verification. The rest of ADR 0004 is unchanged: the independent calc, his governing-case calc, his checklist review, and the 0.5% comparison with rule 2 stops. The independent calc still reads verified entries only, so until the release review it works each drafted value from its own reading of the code. Entries already verified stay verified. After the review the full test suite reruns. Any test case value that depended on a corrected entry is redone from the corrected entry, independent-calc values by a fresh independent calc and his values by him, never by editing them to the tool's new output (CLAUDE.md rules 5 and 6), and each redone value notes the correction. Correcting only a note or edition changes no value (.claude/rules/code-values.md). Decided by Micah, 2026-10-03; docs/brief/verification.md, "The release registry review".

The reason: the engineer of record will not use the tool on real work until v1 is complete. A wrong entry before then reaches no real calc, so verifying slice by slice protects nothing before the release. One review is also more efficient once the set of entries has stopped changing, because a later slice can revise, split or add entries that an earlier slice's review would already have covered.

The cost is that a wrong drafted entry stays in every development calc, under the DRAFT stamp, until the release. Agreement between the tool and the independent calc on a drafted value verifies nothing, because both may hold the same misreading, so until the review the governing-case calc and the checklist review are the only defence on those values. A correction at the review also means redoing the affected test case values.

## Considered Options

- Verify each slice's entries within the slice, before its independent calcs (ADR 0004): a wrong entry is caught within a slice, and the independent calc works from verified values. Replaced by this decision.
- One review of every drafted entry before the v1 release: chosen, because no real calc uses the tool before then and one pass over a settled set of entries costs less.
